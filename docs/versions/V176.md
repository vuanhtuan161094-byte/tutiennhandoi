## Finding

`resolveFirstLifeStory()` is a one-shot settlement lane with real rewards/effects. Live completion writes both:

1. `flow.firstLifeStory.completedBeatIds`, used by the replay guard; and
2. a durable history event shaped as `firstlife.<beatId>.<lifeId>.<actionIndex>` with tags `FirstLife` + `GuidedContent` and `data.beatId`.

Restore previously trusted the completion list independently. If that mirror was lost while the valid current-first-life history event remained, the same beat could execute again after restore and mint its reward/effects a second time.

## Locked authority

- First-life completion after restore is the valid union of authored saved completion IDs and validated history settlement evidence for the current first life.
- History evidence must match an authored beat ID, the current first-life `lifeId`, the live numeric event serial shape, and the `FirstLife` + `GuidedContent` tags.
- `first.choose_path` history is accepted only for authored `sect` / `wanderer` values.
- A proven `first.choose_path` also proves `first.first_clear`, because the live mutation path requires that predecessor before the choice can settle.
- Missing path may be recovered from valid choose-path history; an already-valid saved path is preserved.
- Unknown completion IDs are removed.
- Later-life history cannot create first-life authority.
- The repair is implemented in the already-eager `session-restore.js`; no new eager runtime module is added.

## Proof

`qa/tests/v176-first-life-story-runtime-authority-test.js` covers 6 cases:

1. current-life history reconstructs missing completion;
2. malformed, unknown or wrong-life history cannot forge completion;
3. choose-path history restores path and its proven predecessor;
4. valid saved completion remains monotonic while unknown IDs are removed;
5. later-life history isolation;
6. full `SimulationSession.restore()` blocks replay of the real `first.awakening` reward and does not append a duplicate history event.
